Да. Я собрал требования **из всего текущего брифа, всех 113 ответов и предыдущего контекста проекта**, включая первоначальную идею Google Sheets → Telegram Mini App.

Главная рекомендация: **не делать 15–20 отдельных AI-агентов**. Для такого продукта это быстро превратится в цирк из агентов, которые спорят друг с другом и жрут токены. Лучше сделать **1 оркестратор + 6 специализированных агентов**, причём большинство из них не имеют права напрямую менять данные.

# ТЗ v1.0 — Telegram Mini App для тренера

## 1. Концепция продукта

Система:

**Telegram Bot + Telegram Mini App + Backend API + БД + AI-слой**

Основная модель:

```text
Тренер
   │
   ├── Клиенты
   │      ├── Профиль
   │      ├── Цели
   │      ├── Питание
   │      ├── Замеры
   │      ├── Восстановление
   │      └── Тренировки
   │
   ├── Программы
   │      └── Мезоциклы → недели → дни → упражнения → подходы
   │
   ├── Аналитика
   │
   └── AI-ассистент
          ├── анализирует
          ├── предлагает
          ├── объясняет
          └── ждёт подтверждения тренера
```

Ключевой принцип всей системы:

> **AI предлагает → человек подтверждает → backend выполняет.**

AI **не должен самостоятельно менять** программу, КБЖУ, расписание или данные клиента.

---

# 2. Авторизация и связь с Telegram

Telegram является основной системой идентификации.

Для клиента приоритет связывания:

1. Telegram-контакт/приглашение;
2. Telegram username;
3. Telegram ID — **только если другие способы недоступны**.

То есть ID не должен быть основным пользовательским способом идентификации.

В БД при этом Telegram ID всё равно хранится как технический уникальный идентификатор.

Модель:

```text
Trainer
 ├── telegram_user_id
 └── Clients[]

Client
 ├── telegram_user_id
 ├── username
 ├── display_name
 └── trainer_id
```

На MVP:

> **один тренер → свои клиенты**

Без команд, студий, администраторов и распределения клиентов между тренерами.

Но API лучше спроектировать так, чтобы это можно было добавить позже.

# 3. Профиль клиента

Профиль содержит всё согласованное:

### Основное

* имя;
* отображаемое имя;
* пол;
* дата рождения;
* возраст;
* рост;
* начальный вес;
* текущий вес;
* целевой вес;
* цели;
* приоритеты целей;
* тренировочный стаж;
* уровень подготовки;
* доступное оборудование.

### Ограничения

Структурированные ограничения + свободная заметка.

AI обязан учитывать ограничения.

Если новое упражнение потенциально конфликтует с ограничением:

> ⚠️ Возможный конфликт с ограничением клиента

AI не должен диагностировать заболевание.

---

# 4. Цели

Цель — не просто текст.

Она имеет:

```text
Goal
 ├── название
 ├── приоритет
 ├── KPI
 ├── целевое значение
 ├── диапазон
 ├── срок
 └── статус
```

Можно иметь несколько KPI.

Например:

**Сушка**

* масса: −0,4–0,6%/нед;
* талия: −5 см;
* e1RM жима: не снижать более X%;
* adherence: >90%.

AI может предложить реалистичные диапазоны, но тренер подтверждает.

---

# 5. Конфликт целей

AI должен понимать trade-off.

Например:

> Быстрое снижение веса
>
> * сохранение максимальной силы
> * набор мышц

AI не должен говорить:

> «Сделаем всё».

Он должен сказать:

> Цели конфликтуют. Вот 3 стратегии и последствия каждой.

И предложить варианты.

Финальный выбор — тренер.

---

# 6. Клиентские статусы

Статусы:

* Активный;
* Пауза;
* Неактивный;
* Архив.

Статус изменяет тренер.

Система может давать сигналы:

> ⚠️ Нет тренировки 12 дней.

Но автоматически менять статус не должна.

# 10. Шаблоны программ

Система должна **очень явно показывать режим**, чтобы тренер случайно не изменил программы других клиентов.

## Кастомное упражнение

Тренер может задать:

В шаблоне тренер задаёт:

# 15. RIR

Это одна из ключевых частей системы.

Клиент вводит RIR **тапами**:

```text
0 | 1 | 2 | 3 | 4 | 5+
```

Без ручного ввода.

Сохраняются отдельно:

```text
target_rir
actual_rir
```

Цель может быть:

* фиксированной;
* диапазоном;
* разной для каждого подхода.

Например:

```text
Подход 1 → RIR 3
Подход 2 → RIR 2
Подход 3 → RIR 1
```

---

# 16. Повторы

Плановое значение автоматически подставляется.

Например:

```text
План: 8–10
```

Клиент получает заранее заполненное значение, которое может изменить.

Система хранит:

```text
planned_reps
actual_reps
```

* свободный ввод;

Следующий подход может использовать:

* плановый вес;
* предыдущий фактический;
* правило упражнения;
* AI-рекомендацию.

Но AI только **предлагает**.

# 20. Работа до отказа

RIR 0:

* сохраняется;
* учитывается AI;
* сравнивается с целевым RIR;
* влияет на рекомендации.

Тренер может заранее задать допустимую частоту работы до отказа.

AI может сказать:

> Клиент систематически достигает RIR 0 чаще, чем предусмотрено программой.

И предложить изменение.

# 21. Замены упражнений

получает разрешённый список.

Если альтернативы нет:

> AI предлагает варианты **тренеру**.

Клиент не получает свободную возможность перестраивать программу.

AI в будущем может предложить изменение порядка.

# AGENT 1 — Orchestrator

### Роль

**Главный диспетчер.**

Он не должен сам глубоко анализировать тренировку.

Его задача:

3. собрать результаты;
4. проверить конфликтующие выводы;
5. сформировать финальный ответ;
6. определить, нужно ли подтверждение тренера.

> «Почему у Пети падает жим?»

```text
Data Quality
```

Получает ответы.

И собирает:

> вероятные причины → уверенность → рекомендации.

# Почему не делать AI ответственным за вычисления

Например, не надо спрашивать LLM:

```json
  "weight_14d_avg": 82.9,
  "weight_28d_avg": 83.7,
  "trend_14d": -0.35
}
```

И уже интерпретирует.

Это:

* дешевле;
* быстрее;
* стабильнее;
* тестируемо;
* воспроизводимо.

# Очень важный принцип — AI не пишет напрямую в БД

Например, AI хочет увеличить жим.

Он **не вызывает**:

```text
UPDATE exercise...
```

Он создаёт:

```json
{
  "type": "PROGRAM_CHANGE_PROPOSAL",
  "client_id": "...",
  "exercise_id": "...",
  "old_weight": 80,
  "new_weight": 82.5,
  "reason": "...",
  "confidence": 0.87
}
```

Тренер нажимает:

> **Применить**

Только после этого backend выполняет изменение.

# Все AI-действия должны иметь тип

Я рекомендую такие:

```text
OBSERVATION
WARNING
ANALYSIS
RECOMMENDATION
PROPOSAL
ACTION_REQUIRED
```

Например:

### Observation

> Вес снизился на 0,4%.

### Warning

> Недостаточно данных.

### Analysis

> Производительность выросла несмотря на снижение массы.

### Recommendation

> Рассмотреть сохранение текущих КБЖУ.

### Proposal

> Изменить 2500 → 2400 ккал.

### Action Required

> Требуется подтверждение тренера.

# У каждого агента должен быть Confidence

Не надо писать:

> «AI уверен на 87%»

если это просто декоративная цифра.

Лучше разделить:

### Data confidence

Насколько качественные данные.

### Analysis confidence

Насколько хорошо подтверждается вывод.

### Recommendation confidence

Насколько уверенно стоит предлагать изменение.

Например:

```text
Данные:       94%
Анализ:       81%
Рекомендация: 67%
```

Это гораздо честнее.

# Ещё одна очень важная вещь — память AI

Не отправлять агенту всю БД клиента на каждый запрос.

Нужны три уровня:

### 1. Current Context

Что происходит сейчас.

### 2. Relevant History

Только история, которая нужна для решения.

### 3. Long-term Summary

Сводка клиента:

```text
Цель
Ограничения
Предпочтения
Тренировочная история
Типичная реакция
Стиль тренера
...
```

Это уменьшает стоимость и повышает качество.

# И самое важное архитектурное решение

Я бы строил проект не как:

> **Telegram Mini App + прикрученный ChatGPT**

а как:

> **Training Management Platform + AI Decision Support Layer**

То есть:

```text
                ┌─────────────────────┐
                │      AI LAYER       │
                │                     │
                │  Reasoning/Advice   │
                └──────────┬──────────┘
                           │
                ┌──────────▼──────────┐
                │   DECISION ENGINE   │
                │                     │
                │ Rules + Analytics   │
                └──────────┬──────────┘
                           │
                ┌──────────▼──────────┐
                │     DOMAIN CORE     │
                │                     │
                │ Clients             │
                │ Programs            │
                │ Workouts            │
                │ Nutrition           │
                │ Measurements        │
                │ Recovery            │
                └──────────┬──────────┘
                           │
                ┌──────────▼──────────┐
                │      DATABASE       │
                └─────────────────────┘
```

Это даст тебе возможность сначала запустить **нормальный продукт без AI**, а потом постепенно сделать AI действительно умным, а не просто поставить рядом чатик с GPT.

И ещё один принцип я бы сделал **неизменяемым с самого начала**:

> **AI никогда не должен быть источником истины.**

Истина — **БД + детерминированные расчёты + история действий**.

AI — это **слой интерпретации и принятия решений**, который предлагает тренеру следующий шаг.

Именно такая архитектура, на мой взгляд, лучше всего соответствует всем 113 решениям, которые мы сейчас зафиксировали.
